## 核心目标

开发者打开一份 Eino 运行记录，不执行任何业务逻辑，就能准确回答：

1. 输入是什么？
2. 实际执行了哪些步骤，哪些只是声明或计划？
3. 最终得到什么结果，或在哪里失败、取消、中断？
4. 哪些内容没有采集到，哪些已经脱敏？
5. 每个结论由哪条原始证据支持？

“静态”指读取一份已保存的运行记录并展示其中事实。浏览、展开、查找和完成态步骤
重放都是阅读操作；不会重新执行模型或工具，不需要实时订阅，也不模拟缺失的历史状态。
未完成或只有定义的文件仍可打开，但不能被当作完整执行结果。

工作约定：在以上范围内，发现并确认的技术问题直接修复、补回归并给出验收结果，
不默认停在只读评估。只有明确要求只读，或涉及产品方向变化、破坏性操作、外部发布时，
才停在评估或先确认相应权限。

优先顺序：**展示真实 → 首屏可读 → 复杂结果可查 → 易于嵌入和分享**。
公共重放控制器不再是下一轮的主目标，而是静态结果模型稳定后的接入能力。

### 三个展示板块，一套查看方式

Agent、Graph、Workflow 保留独立入口，导入记录后自动选择，不要求用户选适配器。
共享“输入 → 实际步骤 → 最终结果/异常 → 原始证据”的阅读方式，但不强行统一业务结构：

| 板块 | 重点 | 静态展示约束 |
| --- | --- | --- |
| Agent | 模型回合、工具计划与调用、回答 | 计划不等于执行；Path 看概要，Trajectory 看回合 |
| Graph | 实际访问顺序、循环、重复访问 | 不把重复访问折成同一步；声明图可有环 |
| Workflow | 编排依赖、实际运行步骤与节点结果 | 未执行节点不算成功；原声明留在证据中 |

三个板块不是三套互不兼容的数据产品，也不是执行编辑器或实时监控台。

## 已有基线，不重复建设

- 一份 Run Record，Agent / Graph / Workflow 自动识别。
- 文件、拖放、粘贴导入；错误导入保留原有效结果。
- 明确的运行结束事实，执行结果与采集完整度在数据模型中独立表达。
- Path / Agent Trajectory / Raw 的证据关联和完整 JSON 信封定位。
- 已结束 Agent 的最终记录重放；旧记录保守显示完成状态未知。
- 本地处理，不上传记录；兼容 `eino-workflow-dag@^1.3.1`。

这些是持续回归基线，不能因新增展示能力而退化。

## 首次矩阵评估给出的优先级

首次矩阵扩展只新增测试、真实样例、评估工具与规划。下表保留当时的发现；随后已按
迭代 1 修复前三行中的 4 个错误，Graph I/O 缺口已在迭代 2 补齐。下表是历史发现，不是当前缺陷清单。

| 实测情况 | 当前事实 | 决策 |
| --- | --- | --- |
| Workflow 中途失败 | 源记录正确，但投影将未执行后继标为成功、已失败节点标为 running | 下一轮第一优先级 |
| Agent 原生取消 | 工具实际调用 0 次，却被分配了整次运行的取消错误并标成工具失败 | 先修错误归属与执行/计划区分 |
| Agent 工具中断 | 运行调用已经结束，工具仍显示 running | 静态视图必须表达“中断/结果缺失”，不暗示仍在执行 |
| Graph 循环与取消 | 重复访问、整体终态正确，但 Recorder 未采集节点 I/O 正文 | 补记录能力后再承诺输入输出展示 |
| 嵌套 Workflow 同名节点 | left/shared 与 right/shared 的证据没有串台 | 保留回归，继续测重复/并行/转交，不声称全面支持 |
| 工具恢复、脱敏 | 整体结果正确，恢复内容和脱敏标记保留 | 用作成功但有异常/采集受限的基线 |

### 迭代 1 / P0：先消除错误事实（已实现）

目标：消除本轮 3 个场景中可复现的 4 个状态或归属错误：Workflow 未执行后继被标成功、
失败节点被标 running、Agent 取消误归到未执行工具、工具中断后仍 running。不重做
界面布局；Graph I/O 是下一期的能力缺口，不混入本期修复门禁。

工作：

- Workflow 以原始执行 outcome 为依据；组件只有 input 时，不能覆盖已经记录的 failed。
- 未执行的声明节点不能成为“成功的执行步骤”；保留在声明结构证据中，不推断 skipped。
- Agent 区分工具调用意图与实际调用；全局取消不能仅因只有一个待处理工具就归到它。
- 已结束的静态记录中，缺少步骤结尾应明确表示中断或结果未记录；不得补造结果、时长。
- Path、Trajectory、详情中的同一证据必须得到一致解释。

验收：

- `npm run inspect:recorder-matrix -- --strict` 不再报告本轮状态/归属错误。
- 失败 Workflow 只把 prepare/fail 计入实际步骤；fail 保留源错误，after 没有成功状态。
- 取消样例保留模型的工具计划，但没有“工具实际失败”的错误归因。
- 中断样例展示原始人工批准原因，且不显示工具仍在执行。
- 三浏览器逐项检查上述内容，而不只是检查导入成功和整次运行的状态标题。

严格门禁转绿是必要条件，不是穷尽所有正确性的证明；上述逐项内容与证据验证也必须通过。

### 迭代 2 / P0：完整、易读的运行结果（已验收）

依赖：迭代 1。目标：输入、最终结果/错误、记录完整度在首屏直接可读。

工作：

- 增加统一运行摘要，区分整次最终输出与中间模型回答/工具输出。
- 同时显示执行结果与采集状态：例如“成功 · 部分采集”，失败也不能遮住脱敏/缺失提示。
- 为 Graph 增加受大小限制、先脱敏再序列化的根调用与节点 I/O 采集；不把现有 callback
  元数据当作正文。无法安全采集时给出明确原因，不能虚构内容。
- 保留 definition-only 的结构查看入口，但明确“没有执行记录”，不算成功运行。

验收：

- 三类来源的典型成功/失败文件，不打开 Raw 即可找到输入和最终结果或失败原因。
- 直接回答、恢复成功、取消、中断、部分采集的状态彼此可区分。
- Graph 真实 Invoke 的输入/输出与界面内容逐值一致，脱敏字段不在 Recorder 序列化后的
  JSON 文件中泄漏。
- 补结构化结果、空字符串/null、长文本、超大小限制四类真实 Recorder 场景。
- 不将“元数据捕获完成”扩大解释为“所有业务数据均已捕获”。

### 迭代 3 / P1：实际路径与复杂调用（本期子集已验收）

已验证同名工具并行乱序返回、跨回合重复调用、统一步骤和证据选择；迭代 4 再补真实
Agent-as-tool 父子回答、并发调用身份、局部失败与传播失败，并提供共同的调用目录。
既有循环与嵌套同名场景继续回归。子 Agent 转交及更完整的恢复场景仍是后续候选，
不在本期完成声明内。

依赖：稳定的步骤语义与 I/O。目标：三类来源共享静态检查方式，复杂调用不混淆。

工作：

- Workflow 默认运行视图与 Graph/Agent 一样围绕观察到的执行步骤；声明结构仍保留在
  技术详情作为独立上下文，先不增加新的一级结构切换。
- 建立真实场景：分支未选中、循环重复调用、并行同名工具乱序返回、嵌套同名节点、
  子 Agent 转交。先确认 Eino 提供的身份信息，再决定调用实例键。
- 节点选择、详情和 Raw 导航统一到规范执行对象；没有足够关联信息时显示歧义提示。

验收：

- 同名、同输入、同工具不导致不同调用被错误合并；循环每次访问均可检查。
- 并行返回次序变化不改变结果归属；不可从相邻位置推断并行或因果关系。
- 只声明未运行的节点不进入实际执行计数，嵌套路径与证据对应。
- 嵌入式 Viewer 和工作台点击同一步骤，返回同一规范节点及证据。

### 迭代 4 / P1：长结果与证据阅读（首版随本轮验收）

已交付分页检索、异常定位、完整/未归属证据目录与三档合成基线；超过 500 步按需绘图。
全文检索、全量大图性能优化未包含在首版承诺中。

目标：从演示型短样例推进到真实项目中的文本、结构化结果和长运行记录。

工作与验收：

- 用通用类型规则展示字符串、对象、数组；第 7 轮移除天气等业务字段猜测，不挑选或改写业务结构。
- 长文本/JSON 支持展开与复制，明确区分“界面折叠”与“源内容未采集/已截断”。
- 提供步骤查找、跳到错误/中断、完整证据目录；未归属证据也能主动查阅。
- 先测 100 / 1,000 / 10,000 条证据的加载、选择和内存，再决定分页或虚拟化；压力
  数据必须标注为合成，不能当真实 Recorder 业务覆盖。
- 给定测试机和浏览器后记录基线，性能目标相对基线制定，不先承诺未测量的耗时。

### 迭代 5 / P2：可交付的静态查看能力（本地首版随本轮验收）

已交付完整嵌入组件与离线单 HTML 查看器，并验证原始记录导出、多实例、更新、销毁。
本地可交付不代表已发布；不开展发布、部署或组织治理工作。

目标：不用源码仓库也能查看和共享保存后的记录，保持隐私与证据一致性。

工作与验收：

- 先提供可搬运的本地查看包和原始记录下载，再评估是否需要单 HTML 报告。
- 保存 → 重新打开，原始 evidence 保持一致；记录中的 HTML/脚本只作为文本显示。
- 不引入强制云服务、账户或上传流程；离线方式及浏览器限制写清楚。
- 静态模型稳定后，提取可复用的选择/最终结果重放能力，验证多实例、更新、销毁。

## 如何持续验证

每个新的业务场景都按同一链路验收：

```text
真实 Eino 执行（可用确定性模型替身）
  → 实际 Recorder 产物
  → 不改造业务事实的 golden
  → JS 投影与源事实比较
  → 浏览器中的状态、正文、证据定位
```

验证分层：

- 录制层：执行结果、实际调用次数、结束边界、原始错误、脱敏和大小策略。
- 传输层：Go/JS 校验一致、原记录不被变更、旧文件兼容。
- 语义层：没有假成功、假执行、假错误归属或假运行中；严格评估门禁以此为准。
- 交互层：导入、选择、原始证据、键盘与窄屏；通过这层不能替代语义层。

迭代 1、2 已完成严格门禁和定向浏览器验证；迭代 2 为 20 个场景及三浏览器 195 项检查。
迭代 3 扩大到 22 个场景（21 次真实运行、1 次仅编译定义），三浏览器全套 249 项通过，
最终可读性调整后另复验其中 18 项。各项限制和性能环境见迭代 3 验收记录。
迭代 4 扩大到 26 个场景（25 次真实运行、1 次仅编译定义），三浏览器全套 288 项通过。
Go 并发检查采用隔离的上游 Agent 实例；共享实例的上游竞争复现与其他边界见迭代 4 验收记录。
第 5 轮保持 26 场景，收敛三种交付入口的结果阅读体验；三浏览器全套 **363 项通过**，
增加 75 项展示和交互回归，并完成桌面、窄屏实际视觉检查。
第 6 轮增加两份真实三层 Agent 记录，矩阵为 28 场景；三浏览器全套 **429 项通过**，
局部阅读模型、全部 Go race 检查及严格矩阵均通过，保留既有 4 项明确限制。
不按固定日期承诺尚未验证的复杂调用支持，以每期验收条件控制范围。

## 明确不做

实时回放、在线执行调试器、Workflow 编辑器、APM/告警后台、多运行分析平台、AI
推理解释、未授权的发布部署。`eino-workflow-dag` 保持兼容且不在此计划的修改范围。
